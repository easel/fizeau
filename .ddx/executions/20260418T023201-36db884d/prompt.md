    <description>
## Problem&#xA;&#xA;Current preset names (prompt/presets.go, exposed via cmd/ddx-agent main.go --preset flag) are:&#xA;  agent | benchmark | claude | codex | cursor | minimal&#xA;&#xA;Five of six are named after OTHER harnesses or products (claude, codex, cursor) or internal labels (agent, minimal). This creates real cognitive-load bugs in practice:&#xA;&#xA;- &#39;preset codex&#39; on the embedded &#39;agent&#39; harness is semantically contradictory. &#39;codex&#39; is a HARNESS (OpenAI&#39;s Codex CLI). Using it as a preset name on the ddx-agent invocation implies &#39;use the embedded agent but pretend to be codex&#39; — why not just use the codex harness directly? The preset name should name an INTENT, not another implementation.&#xA;&#xA;- Downstream config files like DocumentDrivenDX/ddx .ddx/config.yaml end up with lines like:&#xA;&#xA;      harnesses:&#xA;        agent:&#xA;          binary: ./ddx-agent&#xA;          base_args: [&#39;--json&#39;, &#39;--preset&#39;, &#39;codex&#39;]&#xA;&#xA;  A reader reasonably assumes this routes through codex. It doesn&#39;t. It runs the embedded ddx-agent with a prompt template styled in a &#39;codex-ish&#39; way. Confusing and load-bearing wrong.&#xA;&#xA;- Preset names encode prompt STYLE (instruction verbosity, tool description format, etc.), not provider choice. Calling that style &#39;codex&#39; pins the meaning to whatever codex happens to do today; when codex changes, the preset either drifts or becomes misleadingly named.&#xA;&#xA;## Proposed rename&#xA;&#xA;Align preset vocabulary with DDx routing profile vocabulary (cheap | fast | smart) and add a &#39;default&#39; for the middle. Explicit intent, no cross-reference to other tools.&#xA;&#xA;  agent      -&gt; default    (neutral prompt, balanced tool descriptions)&#xA;  benchmark  -&gt; benchmark  (unchanged — evals use a named fixture, not a production preset)&#xA;  claude     -&gt; smart      (the richest/most-verbose preset today; used when quality matters and tokens are cheap)&#xA;  codex      -&gt; cheap      (the terse preset today; used when tokens/latency matter)&#xA;  cursor     -&gt; (drop or merge into default) — &#39;cursor&#39; is a specific IDE product, not a prompt-intent category&#xA;  minimal    -&gt; minimal    (unchanged — legitimate style: smallest possible prompt, for latency-critical or low-context use)&#xA;&#xA;Final name set: cheap | default | smart | minimal | benchmark (5, down from 6).&#xA;&#xA;## Migration&#xA;&#xA;1. Add the new names as first-class preset IDs; keep the old names as deprecated aliases that emit a stderr warning on resolution (&#39;preset name &#39;codex&#39; is deprecated; use &#39;cheap&#39; — this warning will be fatal in vX.X.X&#39;). Don&#39;t break downstream configs at first.&#xA;&#xA;2. Update README.md, SD-003, and any other doc that references the old names.&#xA;&#xA;3. After one release with deprecation warnings, remove the old names and upgrade the warning to an error.&#xA;&#xA;4. DocumentDrivenDX/ddx will update its .ddx/config.yaml in a coordinated commit once new names ship.&#xA;&#xA;## Other issues with preset names&#xA;&#xA;- &#39;claude&#39; as a preset name pins Claude-specific prompt conventions into a label that will be wrong if Claude&#39;s prompting conventions change. &#39;smart&#39; is future-proof.&#xA;- Preset naming is exposed in session logs, bead execution evidence, and routing events. Confusing names poison those artifacts for anyone reading them later.&#xA;&#xA;## Out of scope&#xA;&#xA;- Changing what each preset actually DOES (tool description text, instruction style). Only the names.&#xA;- Adding new presets. The rename is a pure renaming exercise until new intent categories emerge.
    </description>
