PROBLEM&#xA;Running `fiz --provider local` (and long bench sessions) leaks orphaned harness subprocesses. Observed 2026-05-27 on the dev host: 366 leaked `gemini` node processes, ~14 GB RSS, accumulated over 15+ hours, all reparented to PID 1 (parents long dead). The same shape applies to any harness whose CLI spawns its own children: on a NORMAL (successful) run the spawned process group is never signaled, so any grandchild the harness CLI itself forked survives fizeau&#39;s exit and orphans.&#xA;&#xA;ROOT CAUSE (file:line)&#xA;- Every harness runner creates a fresh process group via setProcessGroupAttr (Setpgid=true) in internal/harnesses/{harness}/runner_unix.go and ships a killProcessGroup helper that signals the negative pgid.&#xA;- internal/harnesses/gemini/runner.go:274-282 — the cleanup goroutine calls killProcessGroup(cmd) ONLY on `&lt;-ctx.Done()`. On normal completion the `&lt;-stdoutReady` branch wins and the goroutine returns without killing the group. cmd.Wait() (runner.go:286) reaps only the direct child; any process the gemini CLI itself spawned (the gemini main -&gt; gemini worker pairs seen in `ps`) stays in the group, un-signaled, and orphans to PID 1.&#xA;- killProcessGroup (internal/harnesses/{harness}/runner_unix.go) sends a single SIGTERM with no SIGKILL escalation, so even on cancel/timeout a child that ignores SIGTERM survives.&#xA;- A stale-harness reaper exists (service_stale_harness_reaper.go + service_stale_harness_reaper_unix.go terminateOwnedProcessGroup, SIGTERM-&gt;SIGKILL) but NOTHING in the runners registers a harness-sessions/*.json record at cmd.Start(), so the reaper has no PIDs/PGIDs to act on and is effectively a no-op for these leaks.&#xA;- Audit the sibling runners for the same conditional-cleanup shape: internal/harnesses/claude/runner.go:263 &amp; :426, internal/harnesses/codex/runner.go:233, internal/harnesses/pi/runner.go:207, internal/harnesses/opencode/runner.go:204 (spawn via internal/harnesses/exec.go:18 HarnessCommand).&#xA;&#xA;PROPOSED FIX&#xA;1.
