    <title>routing: escalate policy ladder instead of returning no-viable-candidate when the policy band is empty</title>
    <description>
PROBLEM: Unpinned routing can return `no viable routing candidate: N candidates rejected` (NoViableCandidateError, internal/routing/engine.go:369-371) when the requested policy band has zero eligible candidates at that moment — even though eligible, dispatchable candidates exist in an adjacent band (e.g. a healthy subscription harness sitting in the smart band while the request is at the default band). Observed 2026-05-28: with the local fleet down, an unpinned `ddx run` returned &#34;16 candidates rejected&#34; rather than selecting an available claude/codex tier.&#xA;&#xA;ROOT CAUSE: the NoViableCandidateError path does not invoke the existing policy-escalation ladder. `EscalatePolicyLadder` (internal/routing/routehealth/routing_helpers.go:83-120) and `ShouldEscalateOnError` (:124) exist and implement cheap→default→smart escalation, but are not wired into the unpinned no-viable path, so a healthy candidate one band away is missed. Per spec (docs/routing/index.md:17-22, docs/routing/policies.md): unpinned routing should &#34;select the best-scoring viable auto-routable model from the snapshot&#34;; an empty requested band with viable candidates elsewhere should escalate, not hard-fail.&#xA;&#xA;PROPOSED FIX: on NoViableCandidateError for an UNPINNED request, attempt the cheap→default→smart ladder via the existing EscalatePolicyLadder/ShouldEscalateOnError before returning the error. Hard-pinned requests must NOT escalate (they fail with candidate evidence per docs/routing/index.md:31-33).&#xA;&#xA;NON-SCOPE: no change to within-band scoring; no change to hard-pin failure semantics; does not cover the separate default_provider native-path failover (tracked in fizeau-e71ba414).
    </description>
