    <title>CONTRACT-003: add Role + CorrelationID + Power for downstream observability and DDx-side retry/escalation</title>
    <description>
DDx (downstream) needs three contract additions to express retry/escalation and reviewer-pairing intent without becoming a router itself. The additions are pure observability + one return field; whether and how Fizeau evolves role/correlation-aware routing intelligence over time is a Fizeau-internal decision and is NOT specified here.&#xA;&#xA;## Background&#xA;&#xA;DDx today imports github.com/DocumentDrivenDX/fizeau (CONTRACT-003 at docs/helix/02-design/contracts/CONTRACT-003-ddx-agent-service.md). To implement Story 10&#39;s automatic escalation + reviewer pairing without DDx becoming a router (DDx must not pin Provider/Model — the spec calls that out as anti-pattern at line 374), DDx needs:&#xA;&#xA;1. To know the **power** of the model that was actually dispatched, so it can request &#39;next call must be at least one rung stronger&#39; via MinPower without importing catalog code into DDx.&#xA;2. To **tag** calls with what kind of work they&#39;re doing (Role) so Fizeau, telemetry consumers, and session log readers can distinguish implementer / reviewer / decomposer / etc.&#xA;3. To **link** calls that share work context (CorrelationID — e.g., &#39;bead_123:attempt_4&#39;) so reviewer + implementer + retry attempts can be joined in logs and aggregations.&#xA;&#xA;Day 1 these are PURE observability — Fizeau&#39;s routing logic is unchanged. Future Fizeau evolution may use Role/CorrelationID for routing decisions; that&#39;s separate work, not specified by this contract change.&#xA;&#xA;## What changes&#xA;&#xA;ExecuteRequest gains:&#xA;- Role string — normalized: lowercased, alphanumeric+hyphen only, max 64 chars; reject invalid pre-dispatch with typed RoleNormalizationError. Empty = unset.&#xA;- CorrelationID string — normalized: printable ASCII (no control chars, no whitespace except hyphen/colon/underscore), max 256 chars; reject invalid with typed CorrelationIDNormalizationError. Empty = unset.&#xA;&#xA;RouteRequest gains the same two fields with the same normalization (parity with Execute so ResolveRoute previews don&#39;t diverge).&#xA;&#xA;ServiceRoutingActual gains:&#xA;- Power int — catalog-projected power value (per § Catalog Power Projection at line 983) for the actually-dispatched Model. 0 means unknown/exact-pin-only when applicable.&#xA;&#xA;CONTRACT-003 reserved-cross-tool metadata keys list (today: produces_artifact, media_type) extends with:&#xA;- role&#xA;- correlation_id&#xA;Collision behavior: top-level field wins; emit MetadataKeyCollision warning event when caller also sets Metadata[&#39;role&#39;] or Metadata[&#39;correlation_id&#39;]. Future versions may reject duplicates.&#xA;&#xA;Echo behavior: Role + CorrelationID echoed into Final + RoutingDecision event.Metadata, plus session log header (one line per session). NOT echoed into per-event text_delta metadata to avoid per-token bloat (existing Metadata echo path on text_delta still applies for caller-supplied metadata that is NOT these reserved keys).&#xA;&#xA;Selection precedence (line 374) is UNCHANGED for Day 1. Role and CorrelationID are observational only; they do NOT enter the precedence chain. If a future change adds routing-affecting behavior keyed on these fields, the precedence section must be amended at that time.&#xA;&#xA;Routing Policy Test Contract (line 1448) gains minimum statements:&#xA;- Role + CorrelationID are echoed into RoutingDecision + Final events&#xA;- Role + CorrelationID are echoed into the session-log header&#xA;- Role + CorrelationID are NOT echoed into text_delta event metadata&#xA;- Role + CorrelationID never affect eligibility filtering Day 1&#xA;- Without a CorrelationID, routing is unchanged from baseline&#xA;- ResolveRoute and Execute observe identical routing policy for the same correlation-aware request (Day 1: both ignore for routing)&#xA;- Invalid Role / CorrelationID values rejected pre-dispatch with the typed errors&#xA;- ServiceRoutingActual.Power reflects the catalog-projected power of the dispatched Model&#xA;- When caller sets both top-level Role and Metadata[&#39;role&#39;], top-level wins and a MetadataKeyCollision warning is emitted&#xA;&#xA;## What this enables downstream (informational)&#xA;&#xA;DDx will use these fields to:&#xA;- Compute next-attempt MinPower from previous.RoutingActual.Power + rung_step (cost-tier escalation)&#xA;- Tag implementer + reviewer calls with Role for telemetry; share CorrelationID for trace-join&#xA;- Set MinPower = implementer.RoutingActual.Power + 1 on the reviewer call (best-effort &#39;more powerful&#39;); &#39;different provider&#39; is best-effort emergent, not promised&#xA;- When same-provider results on review, log a degradation event for operator visibility&#xA;&#xA;DDx will NOT:&#xA;- Pin Provider/Model&#xA;- Implement any tiebreaker keyed on CorrelationID&#xA;- Define role-specific routing policy&#xA;&#xA;## Out of scope&#xA;&#xA;- Role-specific Fizeau routing policy (config registry, per-role defaults, etc.)&#xA;- Correlation-aware routing intelligence (tiebreakers, diversity bias, learned preferences)&#xA;- Multi-tenant correlation namespacing&#xA;- Cancellation semantics for any future correlation state&#xA;- DDx→Fizeau outcome-feedback API&#xA;- Anything keyed on Role or CorrelationID that affects routing&#xA;&#xA;If Fizeau evolves any of the above, those are separate proposals with their own design docs (correlation-aware routing must specify state lifecycle, multi-tenant boundaries, cancellation behavior, ResolveRoute parity, and full test contract — none of that is in scope here).
    </description>
